# Physical Phone Full Build

This branch is the isolated full-build track for the physical-phone project.

## Branch roles

- `main` — untouched upstream/base phone.
- `physical-phone-dev` — minimal proof-of-concept used only to prove that a real handset can pair to a live FiveM player and control the existing v-phone.
- `physical-phone-full-build` — full implementation track. This branch can be developed aggressively without risking the proof-of-concept test branch.

## Target behavior

A player's real Android/iPhone pairs to the same FiveM character/session and becomes another control surface for the exact same v-phone. The physical handset must not grant any ability the in-game phone does not already have.

The finished bridge should provide:

1. Secure temporary pairing code generated by the live FiveM character.
2. Session token bound to player source + character/session.
3. Mobile browser/app UI served by the FiveM server.
4. The same phone data and permissions as the in-game v-phone.
5. Two-way synchronization for phone state, app data, notifications, calls, messages, banking, garage, contacts, and settings.
6. Reconnect handling when Wi-Fi, FiveM, or the resource restarts.
7. Session invalidation on disconnect/character change/resource stop.
8. No extra game permissions or server-side actions outside the normal v-phone rules.

## Development order

### Gate 1 — transport proof
`physical-phone-dev` test must succeed first:

real phone -> LAN -> FXServer -> paired player -> existing `/vphone` command.

If this fails, fix transport before moving farther.

### Gate 2 — browser session
Move the pairing proof into dedicated physical-phone bridge code and issue a random session token after the one-time pairing code is accepted.

### Gate 3 — generic v-phone callback bridge
Reuse the phone's existing NUI callbacks instead of rebuilding each app's server logic. A physical-browser request should be routed to the paired FiveM client and invoke the same callback handler the in-game NUI would use.

### Gate 4 — server-to-phone event mirror
Mirror the messages already sent with `SendNUIMessage` to the paired physical session so notifications, call state, battery/signal, app refreshes, and other server-driven changes can reach both screens.

### Gate 5 — UI synchronization
Run the same phone frontend in physical-browser mode and keep important navigation state synchronized between the in-game NUI and the handset. The physical browser should use the bridge instead of direct CEF NUI fetch calls.

### Gate 6 — hardening
Add rate limits, token rotation, disconnect cleanup, character checks, request timeouts, replay protection, and clear diagnostics.

## First apps to validate

1. Messages
2. Contacts
3. Bank
4. Garage
5. Calls

Those cover read/write data, notifications, money, framework integration, and live call state. Once those work through the generic bridge, the rest of the phone should require far less special-case work.

## Rule

Do not merge this branch into `physical-phone-dev` during transport testing. The test branch stays small and easy to diagnose. Once the transport proof passes, testing can move directly to this branch.
